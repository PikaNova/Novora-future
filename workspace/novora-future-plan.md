# Novora 未来项目计划（基于 v2.7.3）

**计划性质**：架构与产品路线草案，不代表已实现功能。

**基线**：`novora-remote-audit` 中的 Novora v2.7.3 快照。工作区中的 `work/Novora` 为旧的 v2.5.6 副本，不作为本计划的实现依据。

## 总体判断

Novora 的主线应保持为：

```text
学校考试安排 → 学校服务端 → 教室大屏/客户端 → 设备运行状态 → 学校内运维
```

作者端只负责 Novora 自身的版本、运行质量和授权运维数据，不承载学校考试正文。Agent 是设备控制组件，不是第四个业务端。

路线可行，但必须先补齐数据模型、命令可靠性和权限边界。版本号不应先于前置条件；每一阶段以验收条件决定是否进入下一阶段。

## 三端边界

### 客户端 Client

- 教室大屏、考试/周测显示、离线缓存和本地显示偏好。
- 设备实例注册、心跳、同步状态和有限的页面级控制。
- 只上传经过同意的必要遥测/错误信息。
- 不负责系统级更新、关机、硬件诊断或跨学校管理。

### 学校服务端 School Server

- 学校、年级、班级、考试、周测、账号、权限和审计。
- 客户端同步、设备绑定、设备运行态势和学校内命令队列。
- 支持 Vercel/Neon 和本地 Node/PostgreSQL 两种部署。
- 学校业务数据留在学校服务端，不同步到作者端。

### 作者端 Author Center

- Novora 实例注册、版本信息、公告、遥测和错误聚合。
- 作者人员的权限、数据保留、脱敏和运维审计。
- 默认只读观察；任何进入学校设备的操作都必须由学校授权并可撤销。
- 不直接编辑学校考试、班级或用户数据。

### Agent（组件，不是业务端）

- 运行在教室电脑上的本地服务，作为学校服务端与操作系统之间的受控执行层。
- 第一版只做 Windows 内测，先支持心跳、页面刷新、重新同步和回执。
- Linux、系统级操作、自动更新和硬件诊断必须在 Windows 版本稳定后再做。

## 分阶段路线

### 阶段 0：v2.7.3 稳定基线

**目标**：冻结现有行为，建立后续改造的验证基线。

- 保留 `exam_data`、`majors`、ETag、离线 outbox、ClassIsland API v2 兼容契约。
- 记录当前设备、同步、权限、遥测和本地部署的回归测试。
- 先完成 `npm ci` 后执行 `npm test`、`npm run typecheck:api`、`npm run build`、本地服务冒烟测试。

**出口条件**：现有 2.7.3 测试与构建在完整依赖环境中通过；无未解释的同步/绑定回归。

### 阶段 1：v2.8 学校考试管理基础

**目标**：把现有“编辑/发布/显示”提升为可管理的考试记录体系，不做传统教务系统。

#### v2.8.0 数据基础

- 设计考试元数据实体（可命名为 `ExamRecord`），明确草稿、发布、结束、归档含义。
- 定义 `ExamRecord` 与现有 `MajorExam` 的唯一关联策略。
- 新增表或等价存储前，先写迁移、回滚和旧数据兼容方案。
- 保留现有 `exam_data` 作为运行快照，避免一次性替换同步协议。

#### v2.8.1 管理列表

- 全部/草稿/待开始/进行中/已结束/历史筛选。
- 名称、时间、年级/班级范围和来源筛选。
- 列表分页或限制策略，避免把全部 JSON 快照一次性加载。

#### v2.8.2 详情与编辑入口

- 考试详情、关联大型考试、范围、显示配置和创建/更新时间。
- 管理层负责定位和生命周期；大型考试页继续负责具体科目时间编辑。

#### v2.8.3 快速考试整合

- 快速考试创建记录，保留当前 `publishQuickMajor`、延长、提前结束和转正式行为。
- 明确快速考试结束后是否归档，以及转正式时如何生成新记录。

#### v2.8.4 历史与复制

- 已结束考试只读归档、搜索、详情和复制。
- 复制时生成新 ID，清除原发布状态、实际时间和操作记录。

#### v2.8.5 稳定性

- 旧数据迁移、离线 outbox、ETag 冲突、多管理员并发、ClassIsland 和周测兼容测试。

**阶段 1 不做**：考生账号、报名、座位、监考排班、题库、阅卷、成绩、完整楼控、Agent、作者远程控制。

**出口条件**：创建 → 草稿 → 编辑 → 发布 → 客户端显示 → 结束 → 归档 → 复制的闭环可验证，且 2.7.3 客户端和周测行为不回归。

### 阶段 2：v2.9 学校考试运行中心

**目标**：只在单个学校服务端内提供考试运行态势和可靠操作。

- 统一考试状态计算，避免后台、客户端和态势页各自按时间推断。
- 运行态势：当前考试、下一场、涉及班级、在线/离线/异常设备、最近运行事件。
- 将 `temporary_command` 升级为持久化命令表：状态、创建人、目标、过期时间、幂等键、回执、失败原因。
- 远程操作先限制为页面刷新、重新同步、发送提醒等低风险动作。
- 所有命令写入学校审计日志；高危系统操作暂不开放。

**出口条件**：命令不丢失、不重复执行，能观察成功/失败/超时，并能在并发和断网恢复场景下测试。

### 阶段 3：v3.0 作者端最小可用版

**目标**：建立独立作者服务，而不是把作者功能继续塞进学校 API。

- 实例注册与撤销、版本/提交信息、部署类型和最后上报时间。
- 遥测与错误接收、指纹聚合、采样、脱敏和保留策略。
- 作者端登录、角色权限、操作审计和数据删除流程。
- 公告和版本说明发布；不直接下发学校考试正文。
- 先只读观察，不做远程控制。

**出口条件**：作者端不可用时学校考试仍正常；可证明学校业务数据不会被作者端读取；错误数据可按实例/版本聚合。

### 阶段 4：v3.1 Windows Agent 内测

**目标**：验证真实设备上的受控执行链路。

- Windows 服务、出站连接、设备注册密钥、撤销和重新绑定。
- 心跳、客户端版本/进程状态、页面刷新、重新同步和命令回执。
- 命令签名、过期、幂等、授权期限和本地审计。
- 先在 5–20 台测试设备运行，建立故障和升级回滚数据。

**出口条件**：连续运行稳定、断网可恢复、命令可追踪、授权可撤销；未满足前不扩展 Linux。

### 阶段 5：v3.2 以后扩展

只有阶段 4 稳定后再推进：

- Linux Agent 与 systemd 适配。
- 校区/教学楼/楼层/教室空间模型和楼控中心。
- 批量设备控制、实时日志、灰度更新和失败回滚。
- 作者端远程协助，但必须由学校授权、限时、分级和全量审计。

AI 查询/操作和商业化授权属于更后阶段，必须建立在真实设备数据和稳定命令协议上。

## 关键技术决策

1. **先管理元数据，再改运行快照**：避免把 `exam_data` 单行 JSONB 直接改成破坏性新模型。
2. **学校服务端是业务数据边界**：作者端只收运行所需的最小数据。
3. **轮询心跳不等于实时控制**：现有心跳可支撑状态展示和低频命令，不能宣称实时双向通道。
4. **浏览器随机实例 ID 不等于可信设备身份**：Agent 阶段必须引入注册密钥、撤销和恢复机制。
5. **先 Windows 再 Linux**：减少同时面对安装、权限、服务管理和网络差异的风险。

## 当前明确的不可行/不应承诺项

- 在不新增作者后台、授权协议和命令队列的情况下，实现跨学校远程控制。
- 仅靠浏览器客户端实现可靠的关机、重启、显示器检测和系统更新回滚。
- 仅增加 `exam_records` 表而不处理现有 `majors`、离线 outbox、ETag 和并发写入。
- 在没有空间模型和真实设备归属数据时交付可用的教学楼地图。
- 在没有真实运行数据和安全审计的情况下上线 AI 批量操作或商业化远程运维。

## 计划维护规则

- 每个版本先写数据/API 契约和出口条件，再拆 UI 任务。
- 每完成一个阶段，更新 `task_plan.md`、`findings.md`、`progress.md`。
- 新发现必须记录证据、影响和置信度；错误不得静默重试。
- 任何跨学校数据、远程操作或系统级命令都需要单独的隐私/安全评审。
